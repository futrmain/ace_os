## Running the demo

### Option A — Live demo

1. Go to https://futrmain.com
2. Open the Intercom chat
3. Ask for the assignment demo URL
4. Follow the link to https://ace.futrmain.com
5. If needed, reset the demo
6. Send in facts

### Option B — Build your own

1. Create a `.env` file inside `./ace` and add your OpenAI key:

   ```dotenv
   OPENAI_API_KEY=sk-...
   ```

2. Adjust the source path of every volume in `./ace/compose.yaml` to match your local location.

3. From inside `./ace`, build and start the stack:

   ```bash
   docker compose build mobkit
   docker compose up --force-recreate --no-build mobkit nginx controller seed
   ```

4. Open your browser:

   | Surface | URL |
   |---------|-----|
   | Operator UI | http://localhost:8010 |
   | mobkit console | http://localhost:8010/console |

## Topology

An human operator reports new incidents and appends facts in the chat. 
This goes to a deterministic Python **controller** that enforces the following RCA methodology:
`incident + facts → hypotheses → diagnostic tests → falsify hypotheses`

                +--------------+
                |   Messages   |
                +------+-------+
                       |
                       | Coordinator extracts facts
                       v
                +--------------+
                |    Facts     |<----------------------------+
                +--+--------+--+                             |
                   |        |                                |
  Investigator     |        |   Test_runner                  |
  generates        |        |   falsifies                    |
  hypotheses       v        v   hypotheses                   |
                +--------------+             Coordinator logs|
                |  Hypotheses  |                 test results|
                +------+-------+                     as facts|
                       |                                     |
                       | Investigator generates tests        |
                       v                                     |
                +--------------+                             |
                |    Tests     |-----------------------------+
                +--------------+

Work is logged in a `WorkGraph` that saves all the work done and how items are linked. 

The items content is generated by calling different agents from the mob. Each agent is stateless.

### `coordinator`

- **System prompt (summary):** turn a free-text incident report into a strict JSON object `{title, facts:[{title, detail}]}` — one entry per distinct stated fact, inventing nothing.
- **Input:** the operator's raw chat message.
- **Known limitations:** runs on free text only — a pasted structured payload is parsed deterministically and skips it; how facts get split is the model's call.

### `investigator`

- **System prompt (summary):** given an incident and its facts, propose 2–5 distinct candidate root-cause *claims* (never tasks or questions), grounded strictly in the stated facts (invent no versions, components, or timestamps). Separately, for one hypothesis, propose up to 2 discriminating yes/no diagnostic questions and judge whether the current facts already answer each.
- **Input:** the incident title and all facts so far (plus a single hypothesis and the questions already asked about it when drafting that hypothesis's diagnostic tests).
- **Known limitations:** hypothesis quality is model-bound (weaker models invent details — hence GPT‑4.1); it sees only the facts, not the existing hypotheses, so regeneration batches can overlap (the controller only dedupes exact repeats); the real cause can fall outside its 2–5; a fresh batch is produced only once every hypothesis has been falsified, one batch per operator message.

### `test_runner`

- **System prompt (summary):** given one hypothesis and a numbered fact list, classify each fact as supporting / conflicting / neutral — a *present* fact that contradicts the mechanism is conflicting, merely *absent* data never is — then give a verdict: FALSIFIED if any fact conflicts, otherwise CONSISTENT. It never confirms or "proves" a hypothesis.
- **Input:** one hypothesis and the full numbered fact list — and nothing else.
- **Known limitations:** falsification is LLM judgment — it can miss a genuine conflict (the hypothesis lingers open) or over-call one (a hypothesis is wrongly ruled out); by design it can never confirm, so the system only narrows by elimination and never declares a cause "proven"; seeing one hypothesis at a time, it can't weigh rival hypotheses against each other.
